## Резюме

Проект в `src` представляет собой SPA на vanilla JavaScript с ручной сборкой DOM, собственным helper-слоем `ElementCreator`, хранением данных в `localStorage`, древовидной навигацией и набором шаблонов для policy/preferences UI.

Общее впечатление:

- сильная сторона проекта: модульность на уровне файлов и заметное стремление к переиспользованию
- слабая сторона проекта: жизненный цикл UI не контролируется централизованно
- главный риск: повторное навешивание глобальных обработчиков на header-кнопки и `document`, что уже сейчас может приводить к повторным действиям и удалению нескольких записей одним кликом
- главный архитектурный долг: нет выделенного слоя состояния/контроллеров, поэтому DOM, данные, события и storage смешаны
- главный performance-риск: тяжёлый `policy-en.json` размером около `1.96 MB` импортируется и конвертируется на старте

Итоговая оценка состояния:

- архитектура: `5/10`
- качество кода: `6/10`
- поддерживаемость: `4/10`
- масштабируемость: `4/10`
- тестируемость: `3/10`
- производительность: `5/10`
- безопасность: `5/10`

## Границы аудита

Аудит выполнен только по содержимому `src`, как было согласовано.

Что анализировалось:

- JS/JSON/SCSS/HTML/CSS внутри `src`
- структура модулей
- архитектурные связи
- статические ресурсы, если они влияют на runtime, bundle или поддерживаемость

Что намеренно не анализировалось:

- `package.json` и lock-файлы
- конфиги вне `src`
- CI/CD, Docker, build pipeline вне `src`

Ограничение этого scope:

- оценка зависимостей и инструментов возможна только косвенно, по исходникам и импортам внутри `src`

## Структура `src`

По текстовым файлам:

- `35` JS-файлов
- `11` SCSS-файлов
- `1` JSON-файл
- `2` HTML-файла
- `1` CSS-файл

Ключевые зоны:

- `src/index.js`, `src/index.html`: точка входа
- `src/app/app.js`: orchestration root
- `src/app/components/*`: UI-компоненты и шаблоны
- `src/app/util/*`: DOM helper, form utils, resizable, localStorage
- `src/app/locales/*`: i18n-слой
- `src/assets/styles/*`: глобальные и компонентные стили
- `src/assets/fonts/OpenSans/*`: шрифты и артефакты Transfonter
- `src/app/components/tree-view/policy-en.json`: крупный data-asset для administrative templates

Структурно проект делится на 4 слоя:

1. bootstrap
2. визуальные компоненты
3. утилиты DOM/storage
4. data-assets и локализация

Проблема в том, что на практике эти слои не изолированы: компоненты напрямую читают DOM, мутируют global header, пишут в `localStorage` и шлют события в `document`.

## Архитектура проекта

Текущая архитектура:

- не framework-based
- event-driven через DOM-события и ручные `addEventListener`
- состояние частично хранится в `treeViewState`, частично в DOM, частично в `localStorage`
- view-компоненты создаются через `ElementCreator`
- forms описываются вручную через большие деревья `createElement(...)`

Плюсы:

- простая модель исполнения
- низкий порог входа в runtime
- нет лишней магии фреймворка
- многие блоки уже разнесены по отдельным файлам

Минусы:

- нет единого lifecycle management
- нет cleanup strategy для глобальных listeners
- нет domain-model слоя
- нет typed contracts для данных формы и storage
- UI orchestration распределён между `app.js`, `preferences-view-template.js`, `create/edit/delete` модулями

Фактически это промежуточное состояние между prototype и production UI.

## Критические и важные findings

### Critical 1. Глобальные обработчики дублируются при каждом повторном входе в preferences-экран

Где:

- `src/app/components/templates/preference/preferences-view-template.js:41-82`
- `src/app/components/templates/preference/preferences-view-template.js:323-334`
- `src/app/app.js:29-46`

Проблема:

- `renderPreferencesTemplate()` каждый раз навешивает новые обработчики на глобальные кнопки header (`Create`, `Edit`, `Delete`) и на `document`
- cleanup отсутствует
- в `treeViewState` есть попытка снимать только `btnCreateHandler`, но этот handler нигде не сохраняется, поэтому очистка фактически не работает

Почему это критично:

- повторный заход в экран shortcuts создаёт ещё один набор обработчиков
- один клик по `Delete` может выполнить несколько delete-операций подряд
- часть обработчиков работает на уже удалённых DOM-деревьях, что создаёт stale state и непредсказуемое поведение

Сценарий сбоя:

1. Пользователь несколько раз открывает раздел `Shortcuts`.
2. Каждый раз `btnDelete.addEventListener(...)` вешается заново.
3. Один клик по `Delete` вызывает несколько обработчиков.
4. Первый обработчик удаляет выбранную запись, второй может удалить уже следующую.

Что делать:

- перевести header actions на явную lifecycle-модель
- хранить cleanup-функцию текущего экрана
- использовать `AbortController` или централизованный binder для listeners

Пример направления исправления:

```js
function bindHeaderActions({ btnCreate, btnEdit, btnDelete, onCreate, onEdit, onDelete }) {
  const controller = new AbortController();
  const opts = { signal: controller.signal };

  btnCreate?.addEventListener('click', onCreate, opts);
  btnEdit?.addEventListener('click', onEdit, opts);
  btnDelete?.addEventListener('click', onDelete, opts);

  return () => controller.abort();
}
```

### High 1. Тяжёлый JSON импортируется и конвертируется на старте приложения

Где:

- `src/app/components/tree-view/tree-view-list-data.js:4-7`
- `src/app/components/tree-view/policy-en.json`

Проблема:

- `policy-en.json` весит около `1.96 MB`
- он импортируется eagerly
- сразу после импорта выполняется `convertPolicySection(policyData.Machine)` и `convertPolicySection(policyData.User)`

Последствия:

- лишняя задержка первого рендера
- лишняя нагрузка на память
- bundle inflation
- работа выполняется даже если пользователь никогда не откроет administrative templates

Что делать:

- лениво подгружать policy JSON
- конвертировать только при раскрытии соответствующей ветки дерева
- кэшировать результат после первой загрузки

### High 2. i18n реализована частично и архитектурно не доведена до конца

Где:

- `src/app/locales/translations.js:4-25`
- `src/app/components/header/header.js:16-48`
- `src/app/components/templates/preference/preferences-view-template.js:121-246`
- `src/app/components/workspace/preferences-template-common.js`
- `src/app/components/tree-view/tree-view-list-data.js:11-80`

Проблема:

- есть отдельный i18n-слой с `t()`
- `currentLang` по умолчанию = `en`
- большая часть UI-текстов зашита напрямую в компонентах на русском
- часть дерева использует `t(...)`, часть строк хардкодится напрямую
- текст для tree nodes вычисляется при импортe модуля, а не при рендере

Последствия:

- смешанный язык интерфейса
- изменение языка не приводит к полному обновлению UI
- масштабирование на новые языки будет очень дорогим
- усложняется поддержка и review контента

Что делать:

- все UI-строки перенести в locales
- `treeViewList` строить через factory-функцию, а не как константу, вычисляемую при import time
- отделить language state от конкретных модулей UI

### High 3. Схема данных shortcuts невалидна относительно формы и может молча портиться

Где:

- `src/app/util/mainLocalStorage/shortcuts.js:53-71`
- `src/app/components/templates/preference/shortcuts/preferences-template-shortcuts.js:95-125`
- `src/app/components/templates/preference/create-preference.js:109-124`

Проблема:

- сидовые данные содержат `TARGET_TYPE: 3`
- UI-форма поддерживает только значения `0`, `1`, `2`
- при сохранении `savePreferencesFromModal()` принудительно clamp-ит `TARGET_TYPE` в диапазон `0..2`

Последствия:

- часть исходных данных уже не соответствует UI-контракту
- открытие/сохранение записи может silently изменить данные
- это сигнал отсутствия единой схемы/валидации данных

Что делать:

- ввести schema validation для `shortcuts`
- валидировать seed-данные до записи в storage
- не выполнять silent normalization без явного сообщения или миграции

### High 4. `localStorage` используется без защитного слоя и может уронить UI

Где:

- `src/app/util/mainLocalStorage/shortcuts.js:77-105`
- `src/app/components/templates/preference/edit-preference.js:41-56`

Проблема:

- для `shortcuts` используется прямой `JSON.parse(data)` без `try/catch`
- модуль с сидированием выполняется как side effect при import
- storage API разбросан по нескольким файлам

Последствия:

- повреждённый JSON в `localStorage` способен уронить экран shortcuts
- данные нельзя безопасно мигрировать
- side effects на import усложняют тестирование и предсказуемость

Что делать:

- создать единый storage adapter
- добавить schema-based validation и fallback
- убрать init side effect из import path

## Качество кода и поддерживаемость

### Что хорошо

- код разложен по смысловым каталогам
- есть попытка централизовать создание DOM через `ElementCreator`
- у большинства модулей есть понятные имена
- CRUD для preferences уже выделен в отдельные файлы
- используется BEM-подобная структура CSS-классов
- комментарии и JSDoc встречаются часто

### Что мешает поддерживаемости

#### 1. Слишком крупные orchestration-модули

Особенно:

- `src/app/components/templates/preference/preferences-view-template.js`
- `src/app/app.js`

Они одновременно:

- собирают DOM
- переключают header state
- навешивают listeners
- открывают/закрывают modal
- обновляют таблицу
- знают о storage
- знают о selected row

Это прямое нарушение SRP.

#### 2. Ручное описание форм через сотни вызовов `createElement(...)`

Файл:

- `src/app/components/templates/preference/shortcuts/preferences-template-shortcuts.js`

Проблема:

- форма длинная, декларативно не структурирована
- добавить поле или поменять локализацию дорого
- высок риск copy-paste ошибок

Лучшее направление:

- schema-driven renderer для полей
- отдельный config-объект для field definitions

#### 3. Дублирование placeholder-шаблонов

Файлы:

- `templates-environment.js`
- `templates-folders.js`
- `templates-registry.js`
- `templates-driveMaps.js`
- `templates-networkShares.js`
- `templates-files.js`
- `templates-iniFiles.js`

Сейчас это почти идентичные файлы с разницей в одной строке. Это не страшно по объёму, но плохо масштабируется.

#### 4. В проекте есть мёртвый или полумёртвый код

Примеры:

- неиспользуемые импорты в `src/app/app.js:1,6-10`
- параметр `namePreference` в `preferences-table-shortcuts.js:62,103` фактически не используется
- `window.createElement = createElement` в `src/app/util/element-creator.js:296-298` загрязняет глобальную область и не выглядит необходимым

## Потенциальные баги и уязвимости

### 1. Выбор не-shortcuts экрана может оставлять старые активные кнопки header

Где:

- `src/app/app.js:79-95`
- все `templates-*.js`, кроме `templates-shortcuts.js`

Проблема:

- полноценный header lifecycle есть только у `renderPreferencesTemplate()`
- placeholder-шаблоны не сбрасывают глобальные кнопки и не переназначают действия

Риск:

- кнопки могут оставаться в состоянии, которое больше не соответствует текущему экрану
- часть кликов будет работать по stale closures

### 2. Будущие non-shortcuts preferences уже сейчас сломаны по контракту формы

Где:

- `src/app/components/templates/preference/create-preference.js:64-81`
- `src/app/components/templates/preference/create-preference.js:125-126`
- `src/app/components/templates/preference/delete-preference.js:21-29`

Проблема:

- `resetModalFormToDefaults()` заполняет `tab-basic` только для `shortcuts`
- для остальных preferences в `localStorage` сохраняется только `basicData`
- delete-логика реализована только для `shortcuts`

Итог:

- архитектура форм уже сейчас не переносится на другие типы preferences

### 3. Пустое состояние таблицы создаёт вложенный `.preference__data-table`

Где:

- `src/app/components/templates/preference/preferences-view-template.js:155-159`
- `src/app/components/templates/preference/shortcuts/preferences-table-shortcuts.js:115-129`

Проблема:

- контейнер создаётся снаружи и снова возвращается из `renderPreferencesTableShortcuts()` для empty state

Риск:

- лишняя вложенность
- CSS/layout branching
- хрупкость рендеринга

### 4. Выбор строки дерева масштабируется плохо

Где:

- `src/app/components/tree-view/tree-view-list.js:71-75`

Проблема:

- на каждый клик выполняется `document.querySelectorAll('.tree-item')`

Риск:

- O(n) обход всего дерева на каждое взаимодействие
- при росте policy-дерева UI будет чувствителен к размеру списка

## Производительность

### Основные bottlenecks

1. Eager import крупного JSON и его немедленная конвертация.
2. Полный rebuild части DOM через `innerHTML = ''` и последующий re-render таблицы.
3. Глобальный поиск `.tree-item` на каждый клик.
4. Тяжёлый шрифтовой набор в `src/assets/fonts/OpenSans/*`.

### Отдельно по assets

В `src/assets/fonts/OpenSans` лежат:

- полный набор `eot/ttf/woff`
- `demo.html`
- `stylesheet.css`

Проблема:

- `demo.html` и `stylesheet.css` выглядят как артефакты Transfonter, а не часть приложения
- они создают лишний шум в `src`
- при неаккуратной сборке могут попадать в output без пользы

### UI/CSS performance notes

- `src/assets/styles/set.scss:5` задаёт `min-width: 1200px`
- `src/assets/styles/set.scss:61` жёстко фиксирует width tree view в `432px`
- `src/assets/styles/components/preference.scss:157` фиксирует modal width `408px`

Это упрощает layout, но делает интерфейс плохо адаптируемым и потенциально тяжёлым для маленьких экранов.

## Безопасность

Высокодостоверных уязвимостей уровня remote exploit в пределах audited scope не подтверждено, потому что в `src` нет сети, auth и server-side логики.

Но есть архитектурные security-risks:

### 1. Latent XSS surface через `innerHTML`

Где:

- `src/app/util/element-creator.js:68-71`
- `src/app/util/element-creator.js:158-160`
- `src/app/util/element-creator.js:270-273`

Проблема:

- helper допускает создание DOM из сырых HTML-строк без sanitization

Сейчас это не выглядит как активная эксплуатация, но это опасный API для будущих фич.

### 2. Глобальное экспонирование helper в `window`

Где:

- `src/app/util/element-creator.js:296-298`

Проблема:

- лишний global mutable entrypoint
- ухудшает изоляцию модулей

### 3. Данные из `localStorage` не валидируются

Где:

- `src/app/util/mainLocalStorage/shortcuts.js:98-100`

Проблема:

- любой мусор в storage становится runtime-рискoм

## Масштабируемость, SRP, SOLID, тестируемость

### Архитектурные решения

Оценка: решение приемлемо для прототипа, но не для роста функциональности.

Почему:

- state размазан по DOM, `treeViewState`, `data-*` атрибутам и `localStorage`
- экран preferences фактически является mini-framework внутри одного файла
- новые типы preferences потребуют копирования существующего подхода, а не расширения модели

### Масштабируемость

Оценка: низкая.

Причины:

- отсутствие schema-driven forms
- отсутствие controller/store слоя
- отсутствие lazy loading для data-heavy частей
- жёсткая связка текущего header с конкретным экраном

### Разделение ответственности

Оценка: частично соблюдено на уровне файлов, но нарушено на уровне модулей.

Примеры:

- `app.js` совмещает state management и view dispatch
- `preferences-view-template.js` совмещает layout, interaction, modal orchestration и table refresh
- storage-операции происходят внутри UI-модулей

### SOLID / SRP

SRP нарушается сильнее всего.

OCP тоже страдает:

- чтобы добавить новый тип preferences, нужно менять несколько модулей и копировать логику, а не расширять декларативную схему

### Тестируемость

Оценка: низкая.

Почему:

- почти все функции завязаны на реальный DOM
- есть import-time side effects
- зависимости не инжектируются
- нет unit-test seams
- test files в `src` не найдены

## Рекомендации

### Что исправить срочно

1. Убрать дублирование обработчиков на header/document и ввести cleanup для текущего экрана.
2. Обернуть `localStorage` в safe adapter с `try/catch`, schema validation и fallback.
3. Привести `shortcuts` seed-данные к валидной схеме, убрать silent data coercion.
4. Сделать lazy loading для `policy-en.json` и отложенную конвертацию дерева.
5. Сбросить/переопределить header state при переключении на любой экран, не только shortcuts.

### Что улучшить через refactoring

1. Выделить `PreferencesController` или аналогичный orchestration-layer.
2. Перевести forms на schema-driven генерацию.
3. Вынести storage-логику из UI-компонентов.
4. Преобразовать tree data в factory-функции, а не module-level константы.
5. Убрать повторяющиеся placeholder-модули в единую generic-реализацию.

### Что оптимизировать

1. Lazy import policy JSON.
2. Минимизировать полные DOM rebuild-ы таблицы.
3. Удалить мёртвые font-demo assets из `src`.
4. Снизить жёсткость layout через tokens и responsive breakpoints.
5. Ограничить глобальные DOM-поиски, перейти на scoped queries и event delegation.

## Инженерный профиль разработчика по проекту

Оценка сделана только по наблюдаемому коду и архитектурным решениям в этом проекте.

### Сильные стороны

1. Есть стремление к модульности.
2. Есть попытка построить собственный reusable UI helper (`ElementCreator`).
3. Видно понимание, что CRUD, template и common form sections надо выносить в отдельные модули.
4. Есть задел под i18n, а не полный hardcode с нуля.
5. Есть внимание к UX-деталям: resizable panes, modal tabs, info panel, tree icons, active states.

### Слабые места

1. Lifecycle управления интерфейсом пока недостроен.
2. Нет жёсткого разделения между state, storage и view.
3. Слабый контроль над data contracts и инвариантами.
4. Склонность решать рост сложности копированием UI-кода, а не через декларативную модель.
5. Тестируемость пока не закладывается как архитектурное требование.

### Каких навыков не хватает именно по этому проекту

1. Проектирование устойчивого UI lifecycle.
2. Архитектура client-side state management без утечек обработчиков.
3. Schema-driven form design.
4. Data validation и миграции для persisted state.
5. Тест-дизайн для DOM-heavy приложений.

### Что стоит изучить

1. TypeScript для моделирования UI/data contracts.
2. Паттерны Presenter / MVVM / Controller для frontend без фреймворка.
3. Unit и integration testing для DOM (`Vitest`/`Jest` + `jsdom`).
4. E2E тестирование пользовательских сценариев (`Playwright`).
5. Lazy loading, code splitting и performance profiling.
6. Безопасная работа с HTML и persisted client-side data.
