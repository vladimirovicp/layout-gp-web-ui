# Исправление дублирования обработчиков и lifecycle cleanup

Дата: `2026-03-19`

## Что исправлено

Исправлена проблема, из-за которой при повторном открытии экранов preferences повторно навешивались обработчики:

- на кнопки header (`Create`, `Edit`, `Delete`)
- на `document` для события `preferences-row-select`
- на `document` внутри `resizable()`

Результат:

- обработчики больше не копятся между рендерами
- у текущего экрана появился явный cleanup lifecycle
- при смене выбранного элемента старый экран сначала корректно очищается, потом рендерится новый

## Какие файлы изменены

- `src/app/app.js`
- `src/app/components/templates/preference/preferences-view-template.js`
- `src/app/util/resizable.js`

## Как было

### 1. Не было cleanup текущего экрана

В `src/app/app.js` состояние экрана не хранило функцию очистки. При новом рендере workspace DOM очищался, но глобальные listeners продолжали жить.

### 2. Preferences-экран навешивал глобальные listeners на каждый рендер

В `src/app/components/templates/preference/preferences-view-template.js` при каждом вызове `renderPreferencesTemplate()` заново выполнялись:

- `document.addEventListener('preferences-row-select', ...)`
- `btnDelete.addEventListener('click', ...)`
- `btnEdit.addEventListener('click', ...)`
- `btnCreate.addEventListener('click', ...)`

Из-за этого один и тот же клик мог вызывать несколько обработчиков подряд.

### 3. `resizable()` оставлял слушатели в `document`

В `src/app/util/resizable.js` обработчики `mousemove` и `mouseup` регистрировались в `document`, но никак не снимались. При повторных рендерах preferences-панели их становилось всё больше.

## Как исправлено

### 1. Введён lifecycle cleanup для текущего экрана

В `src/app/app.js` добавлены:

- `currentViewCleanup`
- `cleanupCurrentView()`
- `setCurrentView(view)`

Новая логика:

1. Перед рендером нового экрана вызывается cleanup предыдущего.
2. После рендера новый экран может отдать свою функцию `cleanup`.
3. Эта функция сохраняется в `treeViewState.currentViewCleanup`.

Это убрало накопление глобальных обработчиков между переключениями.

### 2. Preferences-экран переведён на управляемые listeners

В `src/app/components/templates/preference/preferences-view-template.js` добавлены:

- `addManagedEventListener(...)`
- локальный массив `cleanups`
- `preference.cleanup = () => { ... }`

Теперь каждый listener, который может пережить текущий DOM-экран, регистрируется управляемо и добавляет обратный `removeEventListener(...)` в cleanup stack.

Под cleanup попали:

- `document` listener для `preferences-row-select`
- `btnCreate`
- `btnEdit`
- `btnDelete`
- listeners переключения вкладок
- cleanup для `resizable()` у preference-панели

### 3. Header-состояние теперь очищается при снятии экрана

Добавлена функция `clearHeaderButtonState(...)`.

При cleanup:

- снимается `active`
- удаляются `data-preferences-name`
- удаляются `data-preferences-index`

Это убирает stale-state header после ухода со старого экрана.

### 4. `resizable()` теперь возвращает cleanup-функцию

В `src/app/util/resizable.js` функция переписана так, чтобы:

- хранить именованные обработчики
- снимать их через `removeEventListener(...)`
- сбрасывать `cursor` и `userSelect`
- безопасно возвращать no-op cleanup, если аргументы невалидны

Это делает `resizable()` пригодной для экранов с жизненным циклом.

## Что изменилось в поведении

- При повторном открытии `Shortcuts` старые обработчики больше не остаются активными.
- При переключении между элементами дерева предыдущий экран корректно освобождает свои listeners.
- Header больше не хранит старые `data-*` атрибуты от предыдущего preferences-экрана.
- Resizable-панель preferences больше не накапливает глобальные `mousemove` / `mouseup` listeners.

## Почему это решение безопаснее

- очистка теперь привязана к жизненному циклу экрана, а не к отдельной кнопке
- убрана ложная логика снятия только одного `btnCreateHandler`
- cleanup стал идемпотентным: повторный вызов не ломает экран

## Что осталось вне scope этого фикса

- `document.dispatchEvent(new CustomEvent('preferences-row-select', ...))` в таблице shortcuts всё ещё используется как механизм уведомления
- placeholder-экраны preferences пока не получили собственной бизнес-логики
- автоматических тестов на этот сценарий в проекте пока нет

## Ручная проверка

Рекомендуемый сценарий проверки:

1. Открыть `Shortcuts`.
2. Несколько раз переключиться между элементами дерева и снова вернуться в `Shortcuts`.
3. Выделить строку и нажать `Delete`.
4. Убедиться, что удаляется только одна запись за клик.
5. Открыть modal через `Create` и `Edit` после нескольких переключений.
6. Убедиться, что modal открывается один раз, без дублей обработчиков.
7. Поменять размер info-панели несколько раз после повторных заходов на экран.
8. Убедиться, что resize работает стабильно и не деградирует.

## Ограничения проверки

Автоматические тесты не запускались, потому что в рамках `src` тестовая инфраструктура не обнаружена. Исправление проверено статически по коду и по жизненному циклу обработчиков.
